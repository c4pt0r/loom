# RustFS, AWS S3, and Cloudflare R2 object storage

Loom can store Wasm components, inputs, results, shuffle blocks, and manifests in
**RustFS, AWS S3, or Cloudflare R2**. PostgreSQL still stores coordination records,
Actor state, leases, receipts, and small inline inputs. Application code keeps using
`ObjectStore` and `ObjectRef`; it does not depend on S3 APIs.

All clients, workers, native Pi workers, and dashboards in a namespace must use
the same object provider, bucket, prefix, and namespace. `ObjectRef` contains only
a digest. Switching providers does **not** migrate existing objects: use a fresh
namespace/cluster or copy and verify all referenced objects before switching.
There is no silent fallback to PostgreSQL if an S3 object is missing.

## Try RustFS locally

From the repository root, use a separate Compose project so the existing local
cluster keeps its original objects and configuration:

```sh
rf() {
  LOOM_DASHBOARD_PORT=8789 scripts/local-env.sh docker compose \
    -p loom-rustfs -f compose.yaml -f compose.rustfs.yaml "$@"
}
rf --profile tools build cli
rf --profile dashboard up -d --wait postgres rustfs rustfs-init node-a node-b dashboard
rf --profile tools run --rm -T sort
rf --profile tools run --rm -T word-count --print-result
rf --profile tools run --rm cli --namespace lab repl
```

Inside the REPL:

```text
deploy /opt/loom/sort.component.wasm
submit rustfs-sort $module sort_chunk '[8, 2, 5]'
wait $task
result $task
```

The result is `[2,5,8]`. Uploaded components and task results now live in RustFS.
The dashboard at <http://127.0.0.1:8789> reads output previews from RustFS too.

The overlay uses RustFS 1.0.4 with a named data volume. Its initializer creates the
`loom` bucket once. Repeated startup keeps the bucket and its contents. RustFS's
S3 endpoint is <http://127.0.0.1:19000>; its console is
<http://127.0.0.1:19001>. The local-only credentials are `loom-local-access` /
`loom-local-secret-only`, also used by the clients. All exposed ports bind to
loopback. These credentials and plain HTTP are for this local environment only.

`rf down` stops the cluster while preserving data volumes. Do not use `down -v`
unless you intend to delete both coordination state and stored objects.

## AWS S3

Create a bucket in the intended region using your normal provisioning process.
Loom does not create AWS buckets or modify their policies. Configure each process:

```sh
export LOOM_OBJECT_STORE=s3
export LOOM_S3_BUCKET=my-loom-bucket
export LOOM_S3_PREFIX=loom
export AWS_REGION=us-west-2
# Supply AWS credentials through environment variables or a supported runtime role.
export LOOM_DATABASE_URL='postgresql://loom:password@db.example:5432/loom'

loom --namespace production node --id worker-1
# In another terminal with the same configuration:
loom --namespace production repl
```

Leave `LOOM_S3_ENDPOINT` unset for AWS's regional endpoint. TLS and virtual-hosted
requests are the default. Set `LOOM_S3_FORCE_PATH_STYLE=true` when required by a
compatible service. Bucket and prefix names are not embedded in task metadata.

Credentials use the Apache `object_store` S3 provider: `AWS_ACCESS_KEY_ID` and
`AWS_SECRET_ACCESS_KEY`, with optional `AWS_SESSION_TOKEN`, or refreshable EC2
instance, ECS container, and web-identity credentials. Web identity uses
`AWS_WEB_IDENTITY_TOKEN_FILE` and `AWS_ROLE_ARN` (optional `AWS_ROLE_SESSION_NAME`).
Shared `~/.aws/credentials` profiles and AWS SSO are not loaded directly; export
credentials or use a supported role. Docker must receive credentials and any
referenced token files itself; host token-file paths are not automatically mounted.

The runtime needs `s3:GetObject` and `s3:PutObject` for its prefix. Grant
`s3:ListBucket` as appropriate so missing keys can be distinguished from access
denials. Loom uses conditional `PutObject` requests (`If-None-Match: *`). It does
not require object deletion, listing objects, or bucket creation at runtime.
For SSE-KMS buckets, also grant the key permissions required by AWS S3.

The base `compose.yaml` forwards the supported configuration and credential
environment variables. Export them before launching **every** client/worker.
Do not apply the RustFS overlay to an AWS deployment: it intentionally overrides
these values with the local RustFS setup.

## Cloudflare R2

Create an R2 bucket and obtain an **S3 Access Key ID and Secret Access Key** with
Object Read & Write access to that bucket. These are S3 credentials, not a
Cloudflare bearer API token. Loom does not create buckets or credentials.

```sh
export LOOM_OBJECT_STORE=r2
export LOOM_S3_BUCKET=my-loom-bucket
export LOOM_S3_ENDPOINT=https://YOUR_ACCOUNT_ID.r2.cloudflarestorage.com
export LOOM_S3_PREFIX=loom
export AWS_ACCESS_KEY_ID=YOUR_R2_ACCESS_KEY_ID
export AWS_SECRET_ACCESS_KEY=YOUR_R2_SECRET_ACCESS_KEY
unset AWS_SESSION_TOKEN
export LOOM_DATABASE_URL='postgresql://loom:password@db.example:5432/loom'

loom --namespace production node --id worker-1
# In another terminal with the same configuration:
loom --namespace production repl
```

The `r2` preset uses signing region `auto`, even if `AWS_REGION` or
`AWS_DEFAULT_REGION` is set for another workload. Path-style requests and HTTPS
are the defaults. Supply the bucket's **S3 API endpoint** from the R2 dashboard,
without the bucket name in its path. Do not use an `r2.dev` URL or a public custom
domain. For a jurisdiction-restricted bucket, use its jurisdiction endpoint,
for example `https://YOUR_ACCOUNT_ID.eu.r2.cloudflarestorage.com`.

Use the same R2 credentials and storage configuration on the driver, workers,
and dashboard. The base Compose file forwards these variables too; use it
without the RustFS overlay. Use a fresh namespace when switching from another
provider, as existing objects are not copied automatically.

R2 supports the adapter's atomic `If-None-Match: *` uploads, HEAD, and Range GET.
See Cloudflare's [S3 compatibility](https://developers.cloudflare.com/r2/api/s3/api/),
[conditional write guarantees](https://developers.cloudflare.com/r2/reference/consistency/#conditional-writes),
and [S3 credentials](https://developers.cloudflare.com/r2/api/tokens/).

## Configuration

| Environment variable | Default / behavior |
| --- | --- |
| `LOOM_OBJECT_STORE` | `postgres`; also accepts `s3`, `rustfs`, or `r2` |
| `LOOM_S3_BUCKET` | Required for `s3`, `rustfs`, and `r2`; bucket must exist |
| `LOOM_S3_ENDPOINT` | Unset for AWS; required for `rustfs` and `r2` |
| `LOOM_S3_PREFIX` | `loom`; nonempty relative path without `.` / `..` segments |
| `AWS_REGION` / `AWS_DEFAULT_REGION` | `us-east-1` when neither is set; R2 always uses `auto` |
| `LOOM_S3_FORCE_PATH_STYLE` | `true` for `rustfs` and `r2`, `false` for `s3` |
| `LOOM_S3_ALLOW_HTTP` | `false`; explicitly enable for local HTTP RustFS |

The base Compose file preserves each provider's path-style default. An explicit
`LOOM_S3_FORCE_PATH_STYLE=true` or `false` overrides it.

A native RustFS client uses the same configuration as its container peers, except
its endpoint is `http://127.0.0.1:19000` rather than `http://rustfs:9000`.

## Implementation

`loom-object-store-s3::S3Config` constructs an adapter; `configured(namespace,
default_store)` selects one at the application's composition root. The default
adapter is returned unchanged for `postgres`. The contracts, runtime, Wasm host,
and shuffle algorithm have no dependency on the S3 library.

Keys use `<prefix>/v1/<hex-encoded namespace>/<first two digest characters>/<digest>`.
Hex encoding preserves exact namespace identity, including slashes and Unicode.
Writes use SHA-256 addressing and atomic create-if-absent. If another writer has
already published the same key, the adapter reads and verifies its content rather
than overwriting it. Full reads verify the SHA-256 checksum; ETags are not treated
as content hashes.

`size` uses HEAD. `get_range` checks metadata then performs a native Range GET;
it rejects overflow, out-of-bounds ranges, and truncated responses. Empty reads
still check object existence and bounds. Range reads rely on object immutability
and do not download the whole object to recompute its hash. Other applications
must not modify Loom-owned keys.

Payload publication still precedes the durable coordination commit. Failed commits
can leave unreferenced objects; they cannot commit a reference before its upload
succeeds. No automatic deletion or TTL is introduced. Keep data for as long as
any task, retry, Actor, or dataset can reference it.

The current API buffers whole writes and full reads in memory; multipart uploads
and streaming are not implemented. Request/connect timeouts and bounded retries
are configured in the adapter. This is not a claim of production scale or an
HA RustFS deployment.

## Verification

The same provider contract test can run against RustFS, a disposable AWS bucket,
or an R2 bucket:

```sh
# Set LOOM_OBJECT_STORE and the matching configuration/credentials above first.
cargo test -p loom-object-store-s3 --test s3 -- --ignored

# Add PostgreSQL and the bundled research component for the real Wasm test:
export LOOM_TEST_DATABASE_URL="$LOOM_DATABASE_URL"
export LOOM_TEST_COMPONENT="$PWD/target/research-agent.component.wasm"
cargo test -p loom-conformance --test s3 -- --ignored
```

These tests create unique namespaces and retain their small test objects. They
verify binary and empty objects, concurrent idempotent publication, exact range
bounds, missing keys, namespace isolation, independent reopened clients, and real
Wasm execution with PostgreSQL coordination. The integration test also verifies
that referenced payloads never appear in PostgreSQL's blob table.

After starting the RustFS cluster, `python3 scripts/s3_acceptance.py` verifies
three distributed sort tasks, partitioned word count, an Actor/message workflow,
Dashboard result previews,
and the absence of payload rows in PostgreSQL.

With the RustFS Compose overlay, `rf --profile tests build tests` followed by
`rf --profile tests run --rm tests` includes the S3 tests in the existing acceptance
suite. Real AWS/R2 testing requires an explicitly configured test bucket and
credentials; a RustFS run alone does not establish live AWS/R2 verification.

Local verification on 2026-11-10 used RustFS 1.0.4: 45 default workspace tests,
the S3 provider contract test, and the PostgreSQL/S3/Wasm integration test passed.
The Docker acceptance run completed 10 tasks and 3 actor messages across two
online workers; all succeeded. Dashboard preview reads passed and the cluster's
`lab` namespace contained zero PostgreSQL blob rows. A real AWS bucket was not
used for this verification.

The R2 preset has configuration tests and a local HTTP request test that verifies
SigV4 region `auto`, bucket path addressing, and conditional upload headers through
the real S3 SDK. All 47 default workspace tests, Clippy, and the two external
RustFS contract/Wasm integration tests passed after adding R2. No live R2 bucket
was used for this verification.
